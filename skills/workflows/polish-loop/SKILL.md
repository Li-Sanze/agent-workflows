# Polish Loop（多轮打磨）

## 开场声明

启动时先对用户说明（可按任务改写，要点保留）：

> 已进入 polish-loop 多轮反思工作流。当前模型不是最强，但额度充足，这次用多轮内部审计换质量：先写初稿，再由多个审稿视角挑错，核实裁决后重写，循环到收敛（默认 3~8 轮）。过程稿放在 `<工作目录>`，对话里只给交付版本和收敛记录。

## 工作姿态

- **质量来自过程。** 能力一般的模型一次写对的概率低，但"在别人的稿子里挑出具体错误"比"一次写对"容易得多。把任务拆成写、审、改多轮，每一步都更容易做对。
- **额度不是约束，正确性才是。** 多读上下文、多核实、多跑一轮都值得；不要为了省 token 跳过验证、合并步骤，或提前宣布"已经够好"。
- **token 花在过程里，不花在终稿长度上。** 终稿应该比初稿更准、更紧，而不是更长。
- **自己审自己有盲区。** 同一上下文里审自己刚写的东西，容易觉得都对。所以审稿人要换上下文，只看产物和任务说明。
- **审稿人也会错。** 会编造问题，会为了显得有用硬挑刺。所以意见必须带证据，由主持人核实裁决，不照单全收。
- **只用自己。** 全程只用当前宿主和当前模型：写手、审稿人、主持人都是同一个模型的不同角色。不调用其他模型或其他 CLI 做审稿（额度不可知）；跨模型交叉审计是 orca-agent-tab 等编排类 skill 的事，不在本 skill 范围内。

## 角色

- **主持人**（当前会话）：立靶、派审稿人、核实裁决、判停、交付。全程持有任务说明和版本记录。
- **写手**：写初稿和每轮重写。由主持人兼任，因为重写需要连贯的上下文。
- **审稿人**：每轮覆盖 4 个视角。
  - 宿主能提供干净子上下文并沿用当前会话模型时，每个视角一个子代理，不继承作者或其他审稿人的历史。按可用并发并行或分批派出，每批完成收口后再派下一批。
  - 其余情况按 `references/lenses.md` 末尾的"同会话审稿"逐个视角审，交付报告注明"同会话审稿"。

## 流程

### 第 0 步：立靶

1. **读够上下文。** 相关文件、代码、文档、数据都读到；需要时跑命令确认现状。这一步宁多勿少，审稿人的证据核对也依赖它。
2. **写 `brief.md`**（模板见下）。核心是 3~7 条可检查的验收标准，默认均为必达项，增强建议另列。审稿人每轮以它为锚，防止越改越偏。
3. **定类型和视角。** 按主要交付目标而非文件扩展名判断任务类型（方案设计 / 技术文档 / 代码 / 视觉设计与图示 / 分析结论 / prompt 与规范），读 `references/rubrics.md` 对应清单，按 `references/lenses.md` 选组合。含代码的视觉产物同时遵守文末代码任务规则，验证视角按需读取代码、事实或数据清单。
4. **该问就问。** 目标、范围或读者不清楚，且无法从上下文推断、猜错会导致方向性返工时，先停下来问用户；其他不确定点写进 brief 的"假设"一栏，继续推进。
5. **定轮次。** 默认最少 3 轮、最多 8 轮。用户写了"轮数=N"就最少和最多都设为 N；写了"最少 N 轮"或"最多 N 轮"就只改对应边界。

`brief.md` 模板：

```markdown
# 任务
- 目标：
- 交付物：（形态、存放位置）
- 读者/使用者：
- 任务类型：
- 视觉任务补充（仅适用时）：参考图或文字目标；识别目标；必须保留 / 可删项。
## 验收标准
1.
## 约束
## 上下文来源（路径、命令、链接）
## 假设
## 轮次：最少 3 / 最多 8
```

### 第 1 步：写初稿 v1

按 brief 写出完整初稿，不留"待补充"。存为 v1。视觉方向仍需用户拍板时，先展示能判断构图与主体的 v1，确认后再精修；用户已明确方向或授权自主推进时照其授权继续。

### 第 2 步：第 k 轮（审 vk）

**a. 派审稿人。** 提供 `brief.md`、vk、对应检查清单和该视角说明；含代码时提供本轮 `vk-files/` 与 `vk.patch`，范围以 brief 为准。提示词模板见 `references/lenses.md`。

视觉任务由主持人派审前保存或复用与版本绑定的预览：位图可直接使用原图，网页或矢量按目标视口渲染。将版本、视口/尺寸及预览路径记入本轮记录，提供当前版与前版的同条件预览和 brief 参考（图或文字）；首轮可无前版。审稿人只读查看，不承担对比预览的生成；未能提供可查看预览或未实际查看时，视觉验收标为"未验证"。

不给审稿人：写作时的理由、之前各轮的审稿意见和裁决。原因是让每轮都是新鲜视角，不被前面的结论带偏；"上一轮的问题有没有修好"由主持人在裁决时核对。

审稿人只读不改，不在工作区新建任何文件。代码任务的命令验证见"代码任务的额外规则"。

**b. 核实裁决（主持人）。**

- 先核对四视角结果是否完整。失败或截断记入本轮记录，重试或分段补审并保留原范围覆盖；未补齐的视角标为"未验证"，该轮不得计为干净轮。再合并重复意见，统一编号。
- 对每条阻断和重要意见亲自核实：打开对应位置、重跑命令、查原文。核实不了或依据站不住的，驳回并写明原因。
- 只对本轮冻结的 vk 按验收标准逐条判定：满足 / 部分满足 / 不满足；给整体评分（1~10）。下一版的计划或修复不计为本轮通过，修后须在对应版本重新验证。视觉任务分报视觉验收与技术验证状态；任一必达项失败都不能判通过，两者不能相互抵消。含代码产物的技术验证不得标为"不适用"；其他产物仅在确无适用技术要求时说明依据后使用。
- 回归核对：上一轮采纳的问题这一版是否真的解决；上一版好的部分有没有被改丢。
- 写 `round-k/verdict.md`，在 `log.md` 追加一行。

**c. 判停**（规则见下）。不停就进入 d。

**d. 产出 v(k+1)。** 不停就一定要落盘 v(k+1)，下一轮审的就是它，轮次号和版本号始终一一对应。

- 本轮有阻断或重要问题：按下面的修改原则重写。
- 本轮干净（无阻断、无重要）：只吸收低风险的建议项；没有值得吸收的，就把 vk 原样复制为 v(k+1)。不要为了让下一轮有东西可审而制造改动。

修改原则：

- 逐条回应采纳的意见，说明怎么改的；驳回的写明理由。
- 默认定点修改，没被批评的部分不动；只有结构性问题才整体重写，因为整体重写最容易把好的部分改丢。视觉任务的核心辨识或层级问题经修改仍反复出现时，评估回退或重做结构，避免继续堆细节。
- 能删就不加。很多"不清楚"靠删冗余解决，而不是靠加解释。
- 如果 vk 有验收项退步，或验收程度相同但评分降低，就以此前更符合验收、同等验收下评分更高的一版为基础重做。
- 同一处主观取舍来回修改两次，就锁定并记入交付报告，其他部分继续打磨。已核实的错误或不满足验收的写法仍须修正，不能因震荡锁定。

### 判停规则

循环在以下情况停止或暂停：

1. 已跑轮数 ≥ 最少轮数，四视角结果完整、适用验收全部满足且无未验证项，最近连续两轮都没有阻断和重要问题。
2. 达到最多轮数；这只结束循环，不代表验收通过。
3. 出现 brief 无法裁决、需要用户拍板的事项时暂停；回答后更新 brief，从当前轮继续，暂不写 `final.md`。

不要在最少轮数之前因为"看起来不错"就停。

一轮干净之后，下一轮换用 `references/lenses.md` 中的"确认轮"视角，用不同角度复核，而不是让同一批视角再看一遍。

### 第 3 步：交付

1. **选交付版本。** 先筛选满足验收且无阻断、重要问题的版本，再比较评分；没有合格版本时交付最佳草稿及未满足项。放到 brief 指定位置；内容短可直接在对话里给出。
2. **写 `final.md` 并输出精简报告。** 满足判停规则第 1 条时写"完成 ✓"；达到上限时写"达到上限 !"，如实标明交付版本的验收结果与遗留问题。

```
polish-loop <状态>  共 N 轮，交付版本 = vK（验收：通过/未通过；评分 X/10）

视觉任务另列（每轮记录与交付）：视觉=通过/未通过/未验证；技术=通过/未通过/未验证/不适用（说明依据）

| 轮 | 阻断 | 重要 | 建议 | 评分 | 动作 |
|----|------|------|------|------|------|
| 1  | 2    | 5    | 7    | 5    | 重写 |
| 2  | 0    | 0    | 4    | 8    | 继续确认 |
| 3  | 0    | 0    | 2    | 8    | 收敛 |

主要改进：3~5 条，每条一行
驳回与遗留：未采纳的重要意见及理由；仍未解决的问题（视觉任务含与参考目标的差距）
需要你确认：假设、取舍点；没有就写"无"
过程记录：<工作目录>
```

宿主或用户有自己的输出格式约定（统一标题行、Changes 列表等）时，用那个格式包裹上面的内容。

## 工作目录

默认在项目根建 `.polish-loop/<YYYYMMDD-HHMM>-<短主题>/`：

```
brief.md
v1.md  v2.md  ...            文字类：每版全文
v1.patch  v1-files/  ...     代码类：每版改动快照
round-1/critic-<视角>.md     各审稿人意见
round-1/preview-*.*          主持人准备的版本预览；原图可复用
round-1/verdict.md           合并、核实、裁决、评分、判停；记录预览版本/尺寸/路径
log.md                       每轮一行：阻断/重要/建议/评分/动作；视觉任务追加视觉/技术状态
final.md                     终稿报告
```

- 在 git 仓库里时，如果 `.polish-loop/` 还没被忽略，把它追加到 `git rev-parse --git-path info/exclude` 给出的文件（worktree 和子模块里 `.git` 可能不是目录，不要直接写 `.git/info/exclude`）。这只影响本地，不改 `.gitignore`，也不会进提交；写入失败就跳过，不影响流程。
- 没有项目目录（例如纯问答）时，用宿主的临时目录。sandbox 不允许写项目外时，一律放项目内。
- 中断后说"继续"：恢复本会话已绑定的任务目录；未绑定时，只自动恢复唯一匹配当前任务的未完成目录，否则先确认。读取 `brief.md`、`log.md` 和该轮记录，从中断步骤续跑。
- 与其他工作流一起使用时，只负责打磨当前产物，不修改对方的运行状态。

## 代码任务的额外规则

- 产物就是工作区里的真实改动。开工前记录 `git status --short` 作为基线；要改的文件如果原本就有未提交改动，先告诉用户再动手。
- 每版定稿后，把本任务范围内所有改动和新文件的完整内容拷进 `vk-files/`（含已暂存、未暂存、未跟踪文件）；该范围内的已暂存及未暂存 Git 差异另存为 `vk.patch`，新增文件以快照全文为准。回退仅恢复本任务在 `vK-files/` 中的文件，并删除本任务在 vK 之后新建的文件；不使用 `git checkout`、`git stash`、`git reset`。
- 并行的审稿人不要同时跑测试或构建：包管理器锁、构建缓存、端口、覆盖率报告会互相冲突。每轮只由"验证"视角的审稿人运行测试、类型检查、lint 和最小复现，把命令和关键输出写进意见；运行不了的写明原因，相关结论标为"未验证"。其他审稿人只读代码，最多运行 `git diff`、搜索这类只读命令。
- 想补测一个现有测试没覆盖的场景时，用内联命令（如 `python -c`、`node -e`）或写到系统临时目录，用完删除；不在工作区新建测试文件或临时脚本。宿主不能开子代理时，同会话审稿也照此执行。
- 改动范围以 brief 为准。审稿人发现范围蔓延，按重要问题处理。
- 不提交、不推送、不改远端，除非用户另有要求。
