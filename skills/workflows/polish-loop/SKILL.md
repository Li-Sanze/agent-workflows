# Polish Loop（多轮打磨）

## 开场声明

启动时先对用户说明以下内容，措辞可以按任务调整，要点保留：

> 已进入 polish-loop：
> - 流程：按验收标准写稿 → 用反例检查 → 核实后修改 → 回归。
> - 全程只用当前宿主和当前模型。默认 3~8 轮；没有干净子上下文时默认 3~5 轮，并注明是同会话审稿。
> - 过程稿放在 `<工作目录>`。交付时报告实际验收结果、未验证项和剩余风险。

## 工作姿态

- **质量来自过程。** 能力一般的模型很难一次写对，但在现成的产物里找反例容易得多。所以把任务拆成写、审、改多轮来做。
- **预算服务于正确性。** 遵守用户给定的范围和预算，时间优先花在必达项的验证上。预算不够时，如实报告未验证项，或者报告已达上限：
  - 不为了收敛而一直加轮数；
  - 也不跳过必达验证；
  - 终稿要比初稿更准、更紧，而不是更长。
- **换取证路径，不只换视角名。** 同一个模型只换视角名，盲区不会变。多样性要来自检查方法和输入的不同：
  - 读实现，也看实际产物；
  - 走正常路径，也走异常操作序列；
  - 从需求倒推，看要求有没有落地。
- **先写预期，再看产物。**
  - 有干净子上下文时，审稿人先写「应该怎样」，再打开产物。
  - 同会话时做不到真正的盲审，要如实注明「非盲审」。
- **反例比意见可靠。** 判停看两样：反例统计和验收结果，不看自评分。
- **审稿人也会错，主持人更不能把未知当成通过。**
  - 意见要带证据，由主持人核实；
  - 核实不了的保留为「未验证」，不能驳回了事。
- **只用自己。**
  - 写手、审稿人、主持人都由当前模型扮演，不调用其他模型或其他 CLI；
  - 跨模型交叉审计属于 orca-agent-tab 等编排类 skill；
  - 发现超出自审能力的风险时，写进报告，由用户决定是否另行安排。

## 角色

- **主持人**（当前会话）：
  - 立靶、派审稿人；
  - 串行执行反例和故障验证；
  - 核实裁决、判停、交付；
  - 全程保管任务说明和版本记录。
- **写手**：写初稿和每轮重写。由主持人兼任，因为重写需要连贯的上下文。
- **审稿人**：每轮覆盖 4 个视角，每个视角各配一种检查方法，见 `references/lenses.md`。
  - 宿主能提供干净子上下文、并沿用当前模型时：每个视角派一个子代理，不继承作者和其他审稿人的历史。按可用并发并行或分批派出。
  - 不能时：按 `references/lenses.md` 的「同会话审稿」逐个视角审。

## 流程

### 第 0 步：立靶

1. **读够上下文。** 相关文件、代码、文档、数据都要读到，需要时跑命令确认现状。
2. **写 `brief.md`**（模板见下）。
   - 核心是 3~7 条可检查的验收标准，默认都是必达项，每条写明来源（原文位置或用户原话）。
   - 从 `references/rubrics.md` 的「不变量提示」里，挑出符合当前合同的条目，写成本任务的具体说法。
   - 不变量是帮审稿人发现遗漏的提示，不能借此新增用户没要求的能力。
3. **定类型、视角与方法。**
   - 按主要交付目标判断任务类型，不看文件扩展名。类型共六种：方案设计、技术文档、代码、视觉设计与图示、分析结论、prompt 与规范。
   - 读 `references/rubrics.md` 对应的清单，按 `references/lenses.md` 选组合。
   - 含代码的视觉产物，同时遵守「代码任务的额外规则」。
4. **该问就问。**
   - 目标、范围或读者不清楚，又推断不出来，而且猜错会导致方向性返工时，先停下来问用户。
   - 其他不确定点写进「假设」一栏，继续推进。
5. **定轮次。**
   - 默认最少 3 轮、最多 8 轮；没有干净子上下文时，最多改为 5 轮。
   - 用户写了「轮数=N」，最少和最多都设为 N；只写了「最少 N 轮」或「最多 N 轮」，只改对应的那一个边界。
   - 把实际选定的轮次写进 brief。

`brief.md` 模板：

```markdown
# 任务
- 目标：
- 交付物：（形态、存放位置）
- 读者/使用者：
- 任务类型：
- 视觉任务补充（仅适用时）：参考图或文字目标；识别目标；必须保留 / 可删项。
## 验收标准（每条注明来源）
1.
## 不变量（从 rubrics.md 选取并写成本任务的说法；写清对象、时点、范围）
## 约束
## 上下文来源（路径、命令、链接）
## 假设
## 轮次：最少 3 / 最多 8
```

brief 的必达项发生实质变化时：
- 已累计的连续干净轮数归零；
- 受影响的检查全部重做；
- 原记录保留，不删除。

### 第 1 步：写初稿 v1

- 按 brief 写出完整初稿，不留「待补充」，存为 v1。
- 视觉方向还需要用户拍板时，先给出能看出构图和主体的 v1，等用户确认后再精修。

### 第 2 步：第 k 轮（审 vk）

**a. 冻结与派审。**

1. **冻结版本。** 记录本轮受验文件清单：相对路径和 sha256；被删除的路径记为「不存在」。之后的所有检查结果，都绑定到这份清单。
2. **派审稿人。**
   - 给审稿人的材料：
     - `brief.md`、vk；
     - 适用的检查清单；
     - 该视角和该方法的说明；
     - 含代码时，加上 `vk-files/` 和 `vk.patch`。
   - 提示词模板见 `references/lenses.md`。
   - 不给审稿人的：写作理由，以及之前各轮的意见和裁决。上一轮的问题修好没有，由主持人在裁决时核对。
3. **视觉任务另做预览。** 主持人先准备与版本绑定、同条件的当前版和前版预览，并把版本、视口或尺寸、路径记下来。审稿人没有实际查看的，视觉验收标为「未验证」。
4. **审稿人不改交付文件。** 反例和故障验证的执行规则，见文末「代码任务的额外规则」。

**b. 核实裁决（主持人）。**

- **核对结果是否完整。**
  - 四个视角的结果都要齐。失败或截断的，记录下来，重试或分段补审；仍然补不齐的视角标为「未验证」。
  - 合并重复的意见和反例，统一编号。
- **执行反例。** 审稿人给出但没有执行的反例，由主持人串行执行。执行不了、或结果无法判断的，标为「未验证」，并写明原因。
- **核实每条阻断、重要意见，以及每个声称「击穿」的反例。**
  - 有证据证明成立：采纳。
  - 有反证证明不成立，或明确不在 brief 范围内：驳回，并写明依据。
  - 只有猜想、没有定位、也没有可检查的反例：可以驳回，但相关的必达项不能因此判为通过。
  - 缺少环境、材料或可判断的结果：保留为「未验证」，不能当作已排除。
- **按冻结的 vk 逐条判定。**
  - 每条验收标准和不变量，判为满足、部分满足或不满足；
  - 统计本轮反例：新增几个、击穿几个、未验证几个；
  - 修复计划不算本轮通过；
  - 视觉验收与技术验证分别报告，不能相互抵消；
  - 含代码的产物，技术验证不能标「不适用」。
- **回归核对。**
  - 上一轮采纳的问题，这一版是否真的解决了；
  - 上一版好的部分，有没有被改丢；
  - 已击穿过的反例，在这一版上重跑一遍。
- 写 `round-k/verdict.md`，在 `log.md` 追加一行。

**c. 判停**（规则见下）。不停就进入 d。

**d. 产出 v(k+1)。** 不停就一定要落盘 v(k+1)，轮次号和版本号始终一一对应。

- 本轮有阻断、重要问题，或有击穿的反例：按下面的修改原则重写。
- 本轮干净：只吸收低风险的建议；没有可吸收的，就原样复制。不要为了让下一轮有东西可审而制造改动。

修改原则：

- 逐条回应采纳的意见；驳回的写明理由。
- 默认定点修改，没被批评的部分不动；只有结构性问题才整体重写。
- 能删就不加。
- 怀疑出现退步、想回退到旧版时，先用当前 brief 和同一组关键反例重新验证旧版，再比较。不同轮次的检查输入不一样，不能直接拿击穿数比较优劣。
- 同一处主观取舍来回改了两次，就锁定，记进报告。已核实的错误不能因锁定而豁免。

### 判停规则

1. **收敛**，须同时满足：
   - 已跑轮数 ≥ 最少轮数；
   - 四个视角的结果完整；适用的验收标准与不变量全部满足；涉及必达项或不变量的「未验证」全部闭合；
   - 最近连续两轮没有阻断和重要问题；
   - 最近一轮的新反例满足全轮要求（代码至少 5 个，其他至少 3 个）：
     - 先把本轮新增的全部反例合并去重，再分别统计击穿、未击穿、未验证三类；
     - 击穿数和未验证数都必须为 0，未击穿数达到上述下限；不能先剔除击穿或未验证的反例再判停；
     - 「新」指之前没覆盖过的前置状态、输入、操作序列或输出组合。方法可以复用；只改个名字、把一个场景拆成几条，或重复同一个场景，都不算新增。
     - 这个数量只是最低检查量，不能代替必达项和不变量的覆盖。
2. **达到最多轮数。** 循环结束，但不代表验收通过。
3. **需要用户拍板。** 暂停；用户回答后更新 brief，从当前轮继续。

不要在最少轮数之前因为「看起来不错」就停。

**确认轮。** 一轮干净之后，下一轮用 `references/lenses.md` 的「确认轮」组合：
- 保留反方，以及证据或验证视角；
- 至少增加一条与上一轮不同的取证路径：换一种方法，或用同一方法检查新的输入、操作序列或输出；
- 不需要把所有视角和方法全部换掉，也不要求方法在整个任务里首次出现；
- 确认轮之后还要继续时，照此规则安排。

### 第 3 步：交付

1. **选交付版本。**
   - 优先交付最新、满足当前验收、通过了已知关键回归的稳定版本；
   - 旧版要重新验证后才能交付；
   - 没有合格版本时，交付最好的草稿，并列出未满足的项。
2. **绑定证据。**
   - 交付前，核对交付位置的文件清单与已验证版本的清单一致。
   - 从验证到交付之间，任何文件变了，都要先重新验证受影响的项和关键回归，再更新报告。报告里的数字必须来自交付的这一版。
   - 交付后，如果又修改了本任务的交付文件，旧的验收结果就不再代表新版本。要重新验证受影响的项和关键回归，然后更新清单、`final.md` 和报告。这条规则不要求持续监控外部修改。
   - `final.md` 记录交付清单（路径与 sha256）、证据位置和已验证的版本号，不对 `final.md` 本身计算哈希。
   - 在对话里直接交付时，同样保留一份确切的正文作为版本依据。
3. **写 `final.md`，并输出精简报告。**
   - 满足判停规则第 1 条，写「完成 ✓」；
   - 达到上限，写「达到上限 !」，如实写明验收结果与遗留问题。

```
polish-loop <状态>  共 N 轮，交付版本 = vK（验收：通过/未通过）

视觉任务另列（每轮记录与交付）：视觉=通过/未通过/未验证；技术=通过/未通过/未验证/不适用（说明依据）

| 轮 | 阻断 | 重要 | 建议 | 新反例（总/击穿/未验证） | 动作 |
|----|------|------|------|--------------------------|------|
| 1  | 2    | 5    | 7    | 9/4/1                    | 重写 |
| 2  | 0    | 0    | 4    | 7/0/0                    | 确认轮 |
| 3  | 0    | 0    | 2    | 6/0/0                    | 收敛 |

主要改进：3~5 条，每条一行
驳回与遗留：未采纳的重要意见及理由；仍未解决的问题
自审边界与剩余风险：子上下文或同会话（是否非盲审）；实际覆盖的输入、操作与环境；未覆盖或未验证的关键路径；需要外部知识或另行审计的点。没有发现额外风险时写「未发现额外风险，有限检查不代表不存在其他缺陷」
需要你确认：假设、取舍点；没有就写「无」
过程记录：<工作目录>
```

宿主或用户有自己的输出格式约定时，用那个格式包裹上面的内容。

## 工作目录

默认在项目根建 `.polish-loop/<YYYYMMDD-HHMM>-<短主题>/`：

```
brief.md
v1.md  v2.md  ...            文字类：每版全文
v1.patch  v1-files/  ...     代码类：每版改动快照
round-1/manifest.txt         本轮受验文件清单（路径与 sha256）
round-1/critic-<视角>.md     各审稿人的预期、反例与意见
round-1/preview-*.*          主持人准备的版本预览；原图可复用
round-1/verdict.md           合并、执行、核实、裁决、反例统计、判停
log.md                       每轮一行：阻断/重要/建议/新反例/动作；视觉任务追加视觉与技术状态
final.md                     终稿报告、交付清单与证据位置
```

- 在 git 仓库里时，如果 `.polish-loop/` 还没被忽略，就把它追加到 `git rev-parse --git-path info/exclude` 给出的文件。
  - worktree 和子模块里的 `.git` 可能不是目录，不要直接写 `.git/info/exclude`；
  - 这只影响本地，不改 `.gitignore`；
  - 写入失败就跳过。
- 没有项目目录时，用宿主的临时目录。sandbox 不允许写项目外时，一律放在项目内。
- 中断后用户说「继续」：
  - 恢复本会话已绑定的工作目录；
  - 没有绑定时，只有唯一一个未完成目录与当前任务匹配，才自动恢复，否则先确认；
  - 读取 `brief.md`、`log.md` 和该轮记录，从中断的步骤接着跑。
- 与其他工作流一起使用时，只负责打磨当前产物，不修改对方的运行状态。

## 代码任务的额外规则

- **基线。** 产物就是工作区里的真实改动。开工前记录 `git status --short` 作为基线；要改的文件原本就有未提交改动时，先告诉用户。
- **快照与回退。**
  - 每版定稿后，把本任务范围内所有改动和新增文件的完整内容拷进 `vk-files/`，包括已暂存、未暂存和未跟踪的文件；
  - 已暂存和未暂存的差异，另存为 `vk.patch`；
  - 回退时，只恢复本任务在 `vK-files/` 中的文件，并删除本任务在 vK 之后新建的文件；不使用 `git checkout`、`git stash`、`git reset`。
- **执行串行。** 测试、类型检查、lint、构建、反例执行和故障验证，都由主持人串行运行。也可以明确授权「验证」视角，在本轮冻结版本的临时副本里执行。
  - 其他审稿人只提供可以直接运行的步骤或命令；
  - 每条命令都要写明运行目录、目标版本、退出状态和失败位置；
  - 补测用内联命令，或写到系统临时目录，用完删除。
- **新增检查要证明能失败。** 本轮新增或修改的每项验收检查，都要留下三步证据：
  1. 在正常副本上通过；
  2. 在故障副本上，因为目标行为错误而失败；
  3. 恢复后再次通过。

  另外：
  - 加载失败、语法错误、环境错误导致的非 0 退出，不能证明检查有效，除非这项检查本来就是检查这类错误；
  - 同一个故障可以对应多项检查，不必每条断言各造一个；
  - 故障只做在临时副本上，不能触及交付文件和用户数据。异常中断时，同样要恢复或丢弃副本，并核对交付文件没有变化；
  - 无法安全构造的，写明原因，不算已覆盖。
- **范围。** 以 brief 为准。审稿人发现范围蔓延，按重要问题处理。
- **不提交、不推送、不改远端**，除非用户另有要求。
