# 审稿视角

## 审稿人提示模板

派子代理时，把下面模板填好作为它的完整任务。不要附带写作理由或之前各轮的意见。

```
你是 polish-loop 的审稿人，本次视角：<视角名>。
你不是这份产物的作者。你的工作是找出会让它不合格或明显变差的问题，不是夸它，也不是润色它。

先读：
- 任务说明：<brief.md 的绝对路径>
- 待审版本：<vk 的绝对路径>
  （含代码时：阅读本轮 `vk-files/` 与 `vk.patch`，只审 brief 限定的任务范围）
  （视觉任务：<当前版预览路径>、<前版预览路径，首轮可无>及 brief 图/文参考；主持人注明版本和视口/尺寸，审稿人只读查看）
- 检查清单：<rubrics.md 中适用段落，直接贴入；含代码的视觉任务同时贴入代码清单>

你的视角：<该视角的说明，直接贴入>

要求：
- 只读，不修改任何文件，不在工作区新建文件。
- 含代码的任务：<只有"验证"视角写：你负责运行测试、类型检查、lint 和最小复现；补测场景用内联命令或系统临时目录，用完删除。其他视角写：不要运行测试或构建，只读代码，最多运行 git diff、搜索等只读命令。>
- 每条问题都要定位（原文片段、文件:行号，或画面区域与元素），并给出依据：亲自核实过的事实、复现命令及输出，或清楚的推理。只是"感觉不太好"的，不要标成阻断或重要。
- 没有阻断或重要问题时，直接写"本视角无阻断/重要问题"。不要为了凑数编问题，空着比编造好。
- 按严重程度排序，通常最多列 8 条；视觉任务优先 4 条、约 500 字，作为软预算，必要时展开阻断/重要问题及证据。

按以下格式输出：

## 结论
一句话：从本视角看，这一版能否交付。

## 问题
### [P1] <阻断|重要|建议> <一句话标题>
- 位置：
- 问题：
- 依据：<已验证|推测> ……
- 建议改法：

## 如果只能改一处
改哪一处，为什么。
```

## 严重程度

- **阻断**：不改就不能交付。事实错误、逻辑错误、不满足验收标准、代码跑不通或测试失败、安全问题。
- **重要**：明显影响质量或可用性。读者会被误导、需要返工、遗漏关键情况、范围蔓延。
- **建议**：措辞、风格、结构微调、锦上添花。

## 视角库

| 视角 | 关注点 |
|------|--------|
| 逻辑 | 推理链是否完整；前后是否矛盾；有哪些隐含假设；遗漏了哪些情况和边界；结论能否从前提推出 |
| 证据 | 每个事实性断言能否核实：对照代码、文档、数据、原文亲自查；数字、接口、路径、版本号逐个核对 |
| 读者 | 扮演 brief 里的读者或使用者，从头读一遍并试着照做：哪里看不懂、缺什么信息、哪些是废话、读完能不能行动 |
| 视觉读者 | 对照 brief 查看实际画面：主体是否可识别，形态归属、视觉层级与负空间是否妨碍理解；区分可定位的误读与个人偏好 |
| 参照匹配 | 对比 brief 确认的图像或文字目标、当前版与前版：必须保留项是否丢失，变化是否退步；不把自己的风格偏好当要求 |
| 反方 | 找最强的反对意见：什么情况下会出事、有没有更简单或更好的替代方案、最坏输入和最坏场景是什么 |
| 结构 | 结论是否先行；层次是否清楚；术语前后是否一致；篇幅与信息量是否匹配 |
| 可执行 | 照着能不能落地或执行：任务拆分、验收方式、回滚、未决问题是否明确；prompt 有无歧义 |
| 正确性（代码） | 逻辑、边界、错误处理、并发、资源释放；对照需求逐条确认行为 |
| 验证 | 核对适用的技术约束、事实或数据，视觉任务不代判审美；含代码时跑测试、类型检查、lint 和最小复现，补测用内联命令或系统临时目录，不在工作区新建文件；非代码视觉产物按 brief 核对文件、尺寸、来源等，不强制构建或测试 |
| 一致性（代码） | 与周边代码的命名、注释密度、惯用法、错误处理风格是否一致；有没有多余改动或范围蔓延 |

## 按任务类型的默认组合

每轮覆盖 4 个审稿视角。上一轮干净（无阻断、无重要）时，下一轮换用"确认轮"组合。

| 任务类型 | 常规轮 | 确认轮 |
|----------|--------|--------|
| 方案/设计 | 逻辑、证据、反方、可执行 | 读者、结构、证据、反方 |
| 技术文档 | 证据、读者、结构、反方 | 读者（换成新人读者）、逻辑、证据、可执行 |
| 代码 | 正确性、验证、一致性、反方 | 验证、读者（以后来维护者的身份）、正确性、证据 |
| 视觉设计与图示 | 视觉读者、参照匹配、验证、反方 | 视觉读者（专查目标尺寸）、参照匹配（专查前版保留项）、验证（专查适用边界）、反方（专找误读） |
| 分析结论 | 证据、逻辑、反方、读者 | 证据、反方（专找替代解释）、结构、可执行 |
| prompt/规范/skill | 可执行、逻辑、反方、证据 | 读者（以执行这份 prompt 的较弱模型的身份）、结构、反方、可执行 |

主持人可以按任务调整组合，但有两条底线：每轮至少有一个"反方"；产物里只要有可核实的事实、代码或数据，每轮至少有一个"证据"或"验证"视角。

## 同会话审稿

1. 先把 vk 完整写入文件。
2. 逐个视角串行审：每个视角开始前，先写一行"--- 切换为【<视角名>】审稿人：放下上一个视角的结论和作者立场 ---"，再重新从文件读 `brief.md` 和 vk；视觉任务同时重看比较画面与参考。只按该视角和上面的模板写意见，存为 `round-k/critic-<视角>.md`，再进入下一个视角。不要回看前面视角的意见。
3. 审稿时只依据文件内容判断，不引用自己写作时的理由，也不替原稿辩护；辩护留到裁决环节。
4. 交付报告注明"同会话审稿"。
