# 审稿视角与检查方法

## 审稿人提示模板

派子代理时，把下面的模板填好，作为它的完整任务。填写时删去不适用的括号说明。不要附带写作理由，也不要附带之前各轮的意见。

```
你是 polish-loop 的审稿人。本次视角：<视角名>；本次方法：<方法名>。
你不是这份产物的作者。你的工作是找出会让它不合格或明显变差的问题，不是夸它，也不是润色它。

材料：
- 任务说明：<brief.md 的绝对路径>
- 待审版本：<vk 的绝对路径>
  （含代码时：阅读本轮 `vk-files/` 与 `vk.patch`，只审 brief 限定的范围）
  （视觉任务：<当前版预览路径>、<前版预览路径，首轮可无>，以及 brief 中的参考图或文字；只读查看）
- 检查清单：<rubrics.md 中适用的段落与 brief 的不变量，直接贴入>

你的视角：<该视角的说明，直接贴入>
你的方法：<该方法的说明，直接贴入>

按顺序做：
1. 写预期。打开待审版本之前，只依据任务说明、来源材料和检查清单，写 3~8 条预期。
   - 格式：「前置条件 → 输入或操作 → 可观察的结果」，并注明来源。
   - 有效的例子：「已有一条手写草稿 → 追加生成内容后把它删掉，再追加一次 → 生成内容重新出现在草稿末尾，手写部分不变」。
   - 无效的例子：「草稿处理要正确」，因为它没法被反例证伪。
   - 写完保留原样。后来发现某条预期读错了来源，另起一行更正并写明理由，不要直接改掉原文。
2. 看产物。按你的方法检查待审版本，逐条对照预期。
3. 找反例。针对本视角最怀疑的地方，提出具体反例，写清前置条件、输入或操作、预期结果和实际结果。
   - 数量不用凑。全轮的下限由主持人合并四个视角、去重后统计。
   - 确实没有可疑点，就写「未发现可疑反例」。

要求：
- 不修改交付文件，不在工作区新建文件。
- 含代码时：
  - 只有在主持人明确授权、并给出临时副本时，才执行命令；执行规则见 SKILL「代码任务的额外规则」。
  - 其余情况，把反例写成可以直接运行的步骤或命令，交给主持人执行。最多运行 git diff、搜索这类只读命令。
- 每条问题都要定位（原文片段、文件:行号，或画面区域与元素），并给出依据：已核实的事实、复现命令及输出，或清楚的推理。只是「感觉不太好」的，不要标成阻断或重要。
- 反例状态只有三种：
  - 击穿：实际结果不符合预期，暴露了缺陷；
  - 未击穿：实际结果符合预期；
  - 未验证：没有执行，或执行了但无法判断，注明原因。
  没击穿的反例也有价值，说明这个方向已经查过。
- 没有阻断或重要问题时，直接写「本视角无阻断/重要问题」。不要为了凑数编问题。
- 问题按严重程度排序，通常最多 8 条。视觉任务优先列 4 条，约 500 字。

按以下格式输出：

## 预期（注明盲审或非盲审）
1. ……

## 结论
一句话：从本视角看，这一版能否交付。

## 反例
| # | 前置条件与输入/操作 | 预期 | 实际与证据 | 状态：击穿 / 未击穿 / 未验证（注明原因） |

## 问题
### [P1] <阻断|重要|建议> <一句话标题>
- 位置：
- 问题：
- 依据：<已验证|推测> ……
- 建议改法：

## 如果只能改一处
改哪一处，为什么。
```

## 严重程度

- **阻断**：不改就不能交付。包括：
  - 事实错误、逻辑错误；
  - 不满足验收标准或适用的不变量；
  - 代码跑不通或测试失败；
  - 安全问题；
  - 击穿了必达项的反例。
- **重要**：明显影响质量或可用性。包括：
  - 读者会被误导；
  - 需要返工；
  - 遗漏关键情况；
  - 范围蔓延；
  - 新增的检查无法证明能失败。
- **建议**：措辞、风格、结构上的微调，以及锦上添花的改进。

## 视角库（看什么）

| 视角 | 关注点 |
|------|--------|
| 逻辑 | 推理链是否完整；前后是否矛盾；有哪些隐含假设；遗漏了哪些情况和边界；结论能否从前提推出 |
| 证据 | 每个事实性断言能否核实：对照代码、文档、数据、原文亲自查；数字、接口、路径、版本号逐个核对 |
| 读者 | 扮演 brief 里的读者或使用者，从头读一遍并试着照做：哪里看不懂、缺什么信息、哪些是废话、读完能不能行动 |
| 视觉读者 | 对照 brief 查看实际画面：主体是否可识别，形态归属、视觉层级与负空间是否妨碍理解；区分可定位的误读与个人偏好 |
| 参照匹配 | 对比 brief 确认的图像或文字目标、当前版与前版：必须保留的项是否丢失，变化是否退步；不把自己的风格偏好当要求 |
| 反方 | 找最强的反对意见：什么情况下会出事、有没有更简单或更好的替代方案、最坏输入和最坏场景是什么 |
| 结构 | 结论是否先行；层次是否清楚；术语前后是否一致；篇幅与信息量是否匹配 |
| 可执行 | 照着能不能落地或执行：任务拆分、验收方式、回滚、未决问题是否明确；prompt 有无歧义 |
| 正确性（代码） | 逻辑、边界、错误处理、并发、资源释放；对照需求逐条确认行为 |
| 验证 | 核对适用的技术约束、事实或数据，不代替视觉判断审美；含代码时设计测试与反例，经授权后在临时副本中执行 |
| 一致性（代码） | 与周边代码的命名、注释密度、惯用法、错误处理风格是否一致；有没有多余改动或范围蔓延 |

## 方法库（怎么查）

| 方法 | 做法 | 典型能抓到的问题 |
|------|------|------------------|
| 需求倒推 | 从 brief 和来源条款逐条倒推到产物中的落点；找不到落点的是遗漏，与原文不符的是偏差 | 漏项、偷换需求、只做了一半 |
| 读实现 | 读代码或正文本身，沿调用链或论证链往下走 | 边界、错误路径、推理跳跃 |
| 看产物 | 不看实现，只看运行结果、导出文件、截图、渲染后的页面 | 界面与文案错误、各输出之间不一致 |
| 异常序列 | 构造操作序列：做了又撤销、删了又加、切走再切回、重复执行、中途失败或取消、并发 | 状态分叉、去重错误、撤销无效、资源泄漏 |
| 不变量核对 | 拿 brief 中的不变量逐条找反例 | 某条路径另算一遍、数字对不上 |
| 故障注入 | 在临时副本中改坏实现或注入坏输入，确认对应检查因目标行为失败；由主持人或经授权的验证视角执行 | 假绿、写死期望值、只测正例 |
| 删句测试 | 逐段假设删掉，看有没有任何验收项受影响；没有影响的就是冗余 | 废话、重复、补丁式段落 |

## 默认组合

每轮 4 个视角，每个视角配一种方法。同一轮内的方法尽量不重复。上一轮干净时，下一轮用「确认轮」组合，规则见 SKILL 判停一节。

| 任务类型 | 常规轮（视角 · 方法） | 确认轮（视角 · 方法） |
|----------|----------------------|----------------------|
| 方案/设计 | 逻辑 · 读实现；证据 · 需求倒推；反方 · 异常序列；可执行 · 不变量核对 | 读者 · 看产物；结构 · 删句测试；证据 · 需求倒推；反方 · 异常序列 |
| 技术文档 | 证据 · 需求倒推；读者 · 看产物；结构 · 删句测试；反方 · 读实现 | 读者（新人）· 看产物；逻辑 · 读实现；证据 · 不变量核对；反方 · 异常序列 |
| 代码 | 正确性 · 读实现；验证 · 故障注入；一致性 · 需求倒推；反方 · 异常序列 | 验证 · 看产物；反方（以后来维护者的身份）· 不变量核对；正确性 · 异常序列；证据 · 需求倒推 |
| 视觉设计与图示 | 视觉读者 · 看产物；参照匹配 · 需求倒推；验证 · 不变量核对；反方 · 异常序列（极端尺寸、深浅色、长文本） | 视觉读者（专查目标尺寸）· 看产物；参照匹配（专查前版保留项）· 需求倒推；验证（专查适用边界）· 不变量核对；反方（专找误读）· 删句测试 |
| 分析结论 | 证据 · 需求倒推；逻辑 · 读实现；反方 · 异常序列（替代解释、反向数据）；读者 · 看产物 | 证据 · 不变量核对；反方（专找替代解释）· 读实现；结构 · 删句测试；可执行 · 看产物 |
| prompt/规范/skill | 可执行 · 异常序列（按字面执行的边界情况）；逻辑 · 读实现；反方 · 不变量核对；证据 · 需求倒推 | 读者（以执行这份 prompt 的较弱模型的身份）· 看产物；结构 · 删句测试；反方 · 异常序列；证据 · 需求倒推 |

主持人可以按任务调整组合，但要守住三条底线：
- 每轮至少有一个「反方」。
- 产物里有可核实的事实、代码或数据时，每轮至少有一个「证据」或「验证」。
- 每轮至少有一种执行类方法：看产物、异常序列或故障注入。

## 同会话审稿

没有干净子上下文时：

1. 先把 vk 完整写入文件，并冻结本轮清单。
2. **写预期。** 尽量在写稿或改动之前就记下行为预期。已经读过或写过产物的，在每份意见开头注明「非盲审」，不要假称没看过。
3. **逐个视角串行审。**
   - 每个视角开始前，先写一行「--- 切换为【<视角名> · <方法名>】审稿人：放下上一个视角的结论和作者立场 ---」；
   - 从文件重新读取 `brief.md` 和 vk；
   - 按模板写，存为 `round-k/critic-<视角>.md`；
   - 不回看前面视角的意见。
4. **不替原稿辩护。** 审稿时只依据文件内容，不引用写作时的理由；辩护留到裁决环节。
5. **优先执行。** 切换视角只靠一行提示，清不掉作者立场。所以执行类方法的结论比阅读类更可信：反例要尽量实际执行，不能只写推理。
6. 交付报告注明「同会话审稿」。
